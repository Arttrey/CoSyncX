# CoSyncX: запуск мокового MVP

Этот сценарий создаёт отдельные тестовые данные в `/tmp`. Он не подключает VPS,
не меняет настоящий Nexus, не открывает Cursor и не импортирует реальные чаты.
Пока демонстрация проверена только на Linux.

Нужны Python 3.11+, пакет `cryptography`, Git, Syncthing и доступный в `PATH`
`codex`. На этом компьютере `codex` указывает на бинарник расширения Cursor.
Если `cryptography` ещё не установлен, можно создать отдельное окружение:

```bash
# Выполните команды из каталога проекта после его скачивания.
python3 -m venv /tmp/nexus-sync-venv
/tmp/nexus-sync-venv/bin/pip install -r requirements.txt
```

Запуск с этим окружением:

```bash
/tmp/nexus-sync-venv/bin/python demo.py --syncthing --loopback-mss
```

Если `cryptography` уже доступен системному Python, вместо последней команды
можно выполнить `python3 demo.py --syncthing --loopback-mss` из этого каталога.
Опция `--loopback-mss` нужна для обхода обнаруженной проблемы локального TCP в
этом тестовом окружении; она не меняет настройки сети компьютера.

При успехе команда выдаёт JSON с `"state": "COMPLETE"` и путём `directory`.
Внутри созданного каталога находятся синтетические источник, промежуточный узел
и два получателя. Демонстрация проверяет передачу файлов через Syncthing,
зашифрованные снимки чата и секретов, моковый Git и отчёты о зависимостях.
Имена получателей условные: все процессы запускаются на этом Linux.
Начальные тестовые пакеты создаются первым циклом наблюдателя с автоматическим
поиском Git-репозитория и файлов `.env` и `.npmrc`, без ручного списка путей.
Затем демонстрация проверяет отправку последующих изменений. Поиск по именам
не находит все возможные секреты.
Тестовый `.env` в корне Nexus также автоматически обнаруживается и принимается
обоими моковыми получателями в сценарии Syncthing.
Во время работы она также создаёт ещё один тестовый Git-проект и проверяет,
что он автоматически обнаружен и восстановлен у обоих моковых получателей.
Кроме того, новый тестовый чат доставляется в постоянные изолированные профили
двух получателей, пока тестовый процесс Codex у отправителя работает.
Другой синтетический профиль условного Mac отправляет чат через промежуточный
узел условной Windows; все три узла при этом работают на одном Linux.
Условная Windows также отправляет новый чат и его продолжение условному Mac;
для тестового получателя включено экспериментальное объединение настроек.
Условный Mac также отправляет тестовый проект с Git и зашифрованным секретом
условной Windows; последующие изменения обнаруживаются наблюдателями отправителя
и принимаются наблюдателями получателя. Текущая ветка и индекс получателя не
меняются. Папка проектов Linux остаётся Send Only.
Сценарий также отключает один временный узел, передаёт новый тестовый файл на
промежуточный узел и проверяет его получение после повторного запуска. Это
также проверяет передачу зашифрованного снимка нового тестового чата и его
подготовку в изолированном профиле вернувшегося получателя. Это не проверка
всех видов данных при отключении устройства и не проверка интерфейса Cursor.
Для корневого тестового секрета дополнительно проверяются шифрование, доставка
пакета на промежуточный узел и восстановление после возвращения получателя.
Тестовый Git-коммит также доставляется в отдельную ссылку получателя; его
текущая ветка и индекс при этом не изменяются.
Для созданного во время отключения тестового Python-проекта отчёты получателей
содержат наблюдавшийся пакет и тег его Linux-сборки; описание зависимостей
переносится, а `.venv` нет. Тег описывает установленную сборку и не доказывает,
что для других ОС сборок нет.

`dependency_report` указывает на отчёт получателя. В `status_configs` находятся
пути к тестовым конфигурациям для команды статуса:

```bash
/tmp/nexus-sync-venv/bin/python nexus_sync.py summary --config '<путь из status_configs>'
```

Созданная папка в `/tmp` остаётся для просмотра. Файл `demo.key` внутри неё —
только случайный ключ теста; настоящие ключи туда добавлять не нужно.
Расширение статуса подготовлено в `cursor-extension`, но автоматически не
устанавливается и в интерфейсе Cursor не проверялось.
При установленном Node.js его связь с Python можно проверить без окна Cursor,
передав путь к тестовой конфигурации получателя из `status_configs`:

```bash
NEXUS_PYTHON=/tmp/nexus-sync-venv/bin/python node cursor-extension/test-summary-integration.js '<путь из status_configs>'
```

Эта проверка подменяет интерфейс VS Code и не подтверждает отображение статуса
в Cursor. Если используется системный Python, переменную `NEXUS_PYTHON` можно
опустить.

Переход к реальным данным пока не готов: нужно отдельно проверить безопасное
применение чатов в Cursor, сеть и хранение на VPS, а также работу на Windows и
macOS. Подробные ограничения и результаты испытаний — в [EXPERIMENTS](EXPERIMENTS.md).
