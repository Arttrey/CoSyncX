# Движки передачи CoSyncX

CoSyncX поддерживает два режима: отдельный управляемый экземпляр Syncthing с
собственным каталогом и подключение к уже работающему экземпляру. Переключение
не меняет форматы снимков и не означает разрешение записывать в состояние Codex.

## Настройка через CLI без окна

Сборка `cosyncx` содержит CLI в обоих режимах. Команды из исходного кода
вызываются как `PYTHONPATH=src python3 -m cosyncx`; вместо `cosyncx` в примерах
Windows используйте `cosyncx.exe`. Все пути ниже следует заменить на реальные
абсолютные пути текущего устройства.

Для встроенного экземпляра создайте **новый** профиль и запустите его в
отдельном терминале:

```text
cosyncx engine prepare-managed --home <новый-профиль> --gui-port 8385
cosyncx engine run-managed --home <новый-профиль>
```

Для исходного кода без встроенного движка обе команды дополнительно принимают
`--binary <абсолютный-путь-к-syncthing>`. При подключении к существующему
Syncthing эти две команды не нужны.

Для любого режима укажите адрес локального API и конфигурацию *именно этого*
экземпляра. Во встроенном режиме `--config` указывает на `config.xml` внутри
созданного профиля, порт в `--url` должен совпадать с `--gui-port`.

```text
cosyncx engine ping-existing --url http://127.0.0.1:8385 --config <путь-к-config.xml>
cosyncx engine inspect --url http://127.0.0.1:8385 --config <путь-к-config.xml>
```

`inspect` показывает ID устройства, настроенные папки, их режим и состояние
соединений; API-ключ не выводится. Наличие соединения само по себе не доказывает
доставку снимка или его восстановление в Codex. Настройка отдельного устройства
и новой папки выполняется командами:

```text
cosyncx engine add-peer --url http://127.0.0.1:8385 --config <путь-к-config.xml> --device-id <ID-VPS> --address tcp://<адрес-VPS>:<порт>
cosyncx engine add-folder --url http://127.0.0.1:8385 --config <путь-к-config.xml> --folder <ID-папки> --path <существующая-папка> --device-id <ID-VPS> --mode sendonly
cosyncx engine status-existing --url http://127.0.0.1:8385 --config <путь-к-config.xml> --folder <ID-папки>
```

Чтобы управлять передачей архивных чатов, которым уже назначена отдельная
папка Syncthing, укажите её ID и выберите `status`, `off` или `on`:

```text
cosyncx engine archive status --url http://127.0.0.1:8385 --config <путь-к-config.xml> --folder <ID-архивной-папки>
cosyncx engine archive off --url http://127.0.0.1:8385 --config <путь-к-config.xml> --folder <ID-архивной-папки>
cosyncx engine archive on --url http://127.0.0.1:8385 --config <путь-к-config.xml> --folder <ID-архивной-папки>
```

`off` приостанавливает синхронизацию выбранной папки на этом устройстве, а
`on` возобновляет её. Уже доставленные архивы не удаляются с других устройств;
устройства могут получать данные друг от друга, если они настроены отдельно.
Команда не создаёт папку и не устанавливает шифрование: настройте их до `on`.

Эти команды изменяют конфигурацию выбранного экземпляра и могут начать
передачу файлов. На VPS также нужны Syncthing, взаимное добавление устройств и
папки с тем же ID; CoSyncX на VPS не требуется. `sendonly` защищает только
выбранную папку Linux от входящих изменений и не предотвращает пересечение с
ранее настроенными папками других экземпляров Syncthing. Сначала проверьте всё
на отдельной тестовой папке. Реальные чаты и секреты пока не подключайте:
восстановление и шифрование в реальном сценарии не проверены.

`engine add-folder` использует стандартный маркер Syncthing и может создать
`.stfolder` в выбранном каталоге. Эта команда не настраивает шифрование папки;
не применяйте её к активному профилю Codex. Прямая зашифрованная настройка через
CLI пока не реализована и проверяется только на временных данных.

При создании нового встроенного профиля опция `--listen` управляет входящим
TCP-слушателем; исходящие соединения по указанному адресу устройства возможны
и при стандартном loopback-слушателе. Настройки VPS, доступ к порту, резервное
копирование и безопасное распространение ключей следует проверять отдельно.

## Интерфейс

Панель создана на основе интерфейса Syncthing 2.1.7: сохранены работающие
формы папок и устройств, сокращено верхнее меню и добавлено предупреждение о
неподтверждённом переносе чатов Codex. Команды выводят локальный адрес, который
можно открыть в браузере; они не открывают окна автоматически.

Для встроенного движка:

```text
cosyncx ui --managed-home <абсолютный-путь-к-отдельному-профилю> --gui-port 8385
```

Новый профиль по умолчанию доступен только на localhost. Чтобы явно разрешить
сетевой слушатель, при первом создании можно добавить `--listen
tcp://0.0.0.0:22000`; это делает порт доступным в сети в зависимости от настроек
компьютера. Соединение устройств и папки в панели настраиваются отдельно.

Для уже установленного и работающего Syncthing:

```text
cosyncx ui --existing-url http://127.0.0.1:8384 --config <абсолютный-путь-к-config.xml>
```

CoSyncX запускает локальный интерфейс-прокси и не меняет файлы установки или
настройки при подключении. Кнопки настройки в интерфейсе меняют выбранный
Syncthing только по действию пользователя. Пока проверена совместимость с
Syncthing 2.1.7 и локальным HTTP API; управление остановкой и перезапуском
существующего процесса через прокси отключено. API-ключ считывается локально,
не выводится в консоль и не пересылается за пределы localhost.

Переработанный файл Syncthing распространяется по MPL-2.0; источник и лицензия
указаны в `src/cosyncx_gui/UPSTREAM.md` и `src/cosyncx_gui/LICENSE`.

Реализованный экспериментальный запуск:

1. `python tools/build_portable.py --output <новый-каталог>` собирает на
   текущей ОС автономный файл с Syncthing 2.1.7. Необходимы Python,
   зависимости проекта и PyInstaller 6.15+; официальный архив проверяется по
   закреплённому SHA-256. Можно указать `--archive <скачанный-архив>`.
   В каталоге результата находятся программа и лицензии CoSyncX и Syncthing.
2. `cosyncx engine prepare-managed --home <новый-каталог> --gui-port <порт>`
   создаёт отдельный профиль; `cosyncx engine run-managed --home <каталог>`
   запускает его в текущем терминале. Команды из исходников принимают явный
   `--binary <проверенный-файл>` вместо включённого в сборку бинарника.
   Для соединений с другими устройствами пользователь может явно указать
   `--listen tcp://0.0.0.0:<порт>`; без него доступен только localhost.
3. `cosyncx engine ping-existing --url http://127.0.0.1:<порт> --config
   <путь-к-config.xml>` проверяет уже работающий экземпляр. Команда
   `status-existing` дополнительно принимает `--folder <ID>` и возвращает
   состояние локальной папки. Эти две команды ничего не меняют в существующем
   Syncthing. API-ключ берётся из локального файла и не выводится в ответе.
4. Команды `engine add-peer` и `engine add-folder` явно добавляют выбранное
   устройство и новую папку через локальный API. Они не заменяют существующие
   устройства и папки и отклоняют пересекающиеся каталоги. Для начального
   источника используйте режим `sendonly`. Эти команды меняют конфигурацию
   выбранного экземпляра, в том числе если он установлен отдельно.

Новый управляемый профиль по умолчанию ограничен loopback, не содержит папок и
не соединяется с другими устройствами. Для передачи требуется явно настроить
прослушивание, устройства и папки на каждом узле. Автоматическая настройка VPS,
автозапуск и интеграция с наблюдателем CoSyncX ещё не готовы.
Оба режима пока проверены только на Linux с временными тестовыми данными;
сборки Windows и macOS необходимо отдельно проверить на этих системах.

Пока реальное автоматическое применение чатов не проверено. Тесты должны
использовать изолированные временные каталоги и локальные узлы.
